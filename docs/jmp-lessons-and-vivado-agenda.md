# JMP 复盘与 Vivado 迁移检查项

日期：2026-09-12。依据：[JMP 验证记录](jmp-verification-2026-09-11.md)、[接口交付契约](jmp-api-plan.md)。只总结已观察的问题；以下 Vivado 条目是开发要求，不是已完成或已验证能力。

## 上一轮实际遇到的问题

| 问题与最早出错层 | JMP 中的证据与处理 | Vivado 应沿用的检查 |
| --- | --- | --- |
| 交付目标理解偏差 | 最初 AI 只返回语义操作，由固定编译器生成 JSL；这不满足“AI 返回应调用的接口及参数”。升级为模型明确提供 apiCall，本地只检查合法性、参数和对象引用 | 开发前明确交付为接口调用 JSON；Tcl 是执行接口，不用本地补填命令冒充模型选择，也不把可运行 Tcl 当主要交付 |
| 点击完成不等于画面完成 | 普通 after 在确认后约230ms采集，缺少最终报告。增加保留真实时间的空闲延迟后图，新样本捕获到最终报告 | 区分点击启动、运行中、完成、失败；长耗时任务不能照搬800ms延迟当完成信号。保留前态、关键设置、最终状态，无法确认就记 pending/unknown |
| 输入事件不包含粘贴内容 | Computer Use 的输入表现为 Ctrl+V，键盘日志没有实际数值；不能从按键记录恢复被粘贴文本 | 源文件路径、HDL/XDC代码与参数可能不可见；截图/事件不足时保留输入依赖或未解决项，不凭文件名编造文件内容，也不默认读取剪贴板或私有工程 |
| 跨段操作标签碰撞 | 多段都使用 op-1，本地合并失败，但表/列身份没有冲突。对操作标签加段级命名空间后，离线复用原响应成功 | 操作标签、稳定工程/文件集/运行对象身份分开。标签可按契约规范化；引用身份不得为消除错误而随意重命名 |
| 分段完整性含义不清 | 模型可能把“录制尚未结束/对话框仍打开”当成 false，且不给遗漏原因；末段 true 也不能清空前段遗漏 | complete 只描述已完成的持久操作覆盖；pending独立。每段即时校验，false须有证据和原因，矛盾立即停，不继续消耗请求 |
| 网络错误与语义错误混淆 | 曾出现本机EACCES、TLS bad record MAC，均没有可确认模型返回。后续限定单进程TLS1.2后成功，但不能据此认定服务端故障 | 分开本地权限、传输、服务响应、结构与语义错误。默认无自动重试，有总尝试上限；保留检查点，失败不重发已成功段。不关闭证书验证或全局强制旧TLS |
| 原生接口有默认行为 | 首次 New Table 后追加列产生隐式默认列；构造时显式定义初始列并检查列数后通过 | 查目标版本接口和默认对象；验证工程属性、文件集、目标器件、运行依赖，不能只验证命令无报错。允许的调用组合必须写进执行契约 |
| 旧验证不能证明新链路 | 旧固定JSL成功不等于新的模型接口计划成功；后来对新JSON逐接口执行，保存重开并对照源真值才通过 | 分开模拟响应、原生合成执行、真实VLM与源录制对照。检查脚本遵从JSON，而不是重建一个看似相同的最终结果 |
| 本机代码与VM安装包不同步 | 新分析器在本机运行；VM仍是旧录制器包，不能说全链路已升级 | 记录采集器、分析器、接口目录、执行器的版本/哈希和所在主机。打包白名单，不带.env、录制或请求体 |
| 小样本也可能输入成本高 | 26条事件对应27张不同内容截图、3段分析；事件少不意味着图像token少。当前没有证明普遍降本 | 上传前提供实际图片清单、去重、分段预算；不为了降本丢掉关键小字/成对证据。成功usage与无usage失败分开，不凭MB报价 |
| 测试范围过宽会启动别的应用测试 | 一次未限定目录的node --test误发现既有3ds Max原生测试，随后中断；正式回归限定tests/*.test.mjs | 先读测试副作用，显式列出离线文件，原生执行单独授权/运行；不把全仓库自动发现当安全单元测试 |

## 已解决与仍未解决

- 已解决并在本样本验证：初始默认列、跨段操作标签合并、延迟截图的采集收益，以及新JSON接口计划的原生执行；保存重开后3行1列、数据和Distribution统计与独立源真值一致。
- 已有离线回归和真实分析检查：完整性冲突即时拒绝、pending与遗漏分离、合法对象绑定、预算/检查点；不等于任意流程都识别准确。
- 未解决/未覆盖：通用异步完成检测、通用剪贴板或不可见源文件恢复、全部JMP功能、视频-only、UIA关闭实机对照、自动报告统计提取、生产级通用接口执行器和VM全量升级。
- 网络后续成功只是当前请求可用，不是普遍根因结论；没有把换TLS配置当作所有适配器默认修复。

## Vivado 接下来的顺序

1. 核实VM2实际安装版本、语言、器件及相关许可；历史记录为Vivado ML Enterprise 2024.2，尚不能直接视为本轮观察。
2. 先扫描Home/New Project、工程设置、Sources、Flow Navigator和必要对话框；静态层级与实机布局分开，未扫描项标记未扫描。依据相同版本AMD官方文档建立有界Tcl接口目录。
3. 定义工程、文件集、源文件、约束、设计与运行对象身份；明确输入文件如何交付。源代码未记录或文件缺失时不得输出假完整工程。
4. 实现独立Vivado录制/分析入口和明确的apiCall JSON；复用证据、预算、检查点与验证原则，不照搬JMP行列或报告概念。先选择可实测的小闭环，再扩展综合、实现、仿真或IP流程。
5. 验证接口参数、依赖与不支持路径，加入名称/器件/源文件变化的合成回归。执行只能写入新隔离工程；不默认连接硬件、编程FPGA、覆盖工程或调用任意Tcl/系统命令。
6. 在Vivado中做合成原生执行、保存重开与独立结果对照。付费分析前另确认具体录制、上传范围和请求上限；最终分别报告编码、离线、原生、真实录制四个层级。

首轮不承诺所有器件/IP、bitstream或硬件功能可用。遇到许可、安装组件或必须由用户提供的输入依赖，先明确缺口，不用替代数据或简化工程冒充还原。
